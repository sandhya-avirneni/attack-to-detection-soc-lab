# MITRE ATT&CK Mapping

## 1. Overview

This document maps the activities performed in the Attack-to-Detection SOC Lab to relevant techniques in the MITRE ATT&CK framework.

The objective is to demonstrate how SOC analysts connect observed security events with adversary behaviors during detection engineering and incident investigation.

The mappings are based on controlled lab simulations and available security telemetry.

## 2. ATT&CK Technique Mapping

| Lab Activity | MITRE ATT&CK Technique | Tactic | Evidence Source |
|---|---|---|---|
| Nmap service enumeration | T1046 — Network Service Discovery | Discovery | Nmap scan output |
| Repeated SSH authentication attempts | T1110 — Brute Force | Credential Access | Ubuntu authentication logs |
| Linux account-information access | T1087.001 — Account Discovery: Local Account | Discovery | Linux auditd |
| Command-execution monitoring | T1059 — Command and Scripting Interpreter (contextual reference) | Execution | Linux auditd |

**Important:** T1059 is included as a contextual reference for command-execution telemetry. The benign commands used during validation do not independently establish malicious execution.

## 3. T1046 — Network Service Discovery

**Tactic:** Discovery

**Technique:** [T1046 — Network Service Discovery](https://attack.mitre.org/techniques/T1046/)

### Simulation

Nmap was executed from Kali Linux against the Ubuntu endpoint.

```bash
nmap -sV 192.168.56.103
```

### Observations

- The Ubuntu endpoint was reachable.
- SSH was identified on TCP port 22.
- Service enumeration provided information about the target's exposed services.

### Detection Considerations

Potential detection opportunities include unusual port-scanning patterns, repeated connection attempts, and network traffic associated with service enumeration.

The lab documented Nmap output but did not implement an automated network-scanning alert.

## 4. T1110 — Brute Force

**Tactic:** Credential Access

**Technique:** [T1110 — Brute Force](https://attack.mitre.org/techniques/T1110/)

### Simulation

Repeated SSH authentication attempts were performed against the Ubuntu endpoint using the non-existent username `fakeuser`.

**Attacker IP:** `192.168.56.101`

**Target IP:** `192.168.56.103`

### Log Investigation

```bash
sudo grep -aE 'Failed password|Invalid user' /var/log/auth.log | tail -20
```

### Observations

- Failed SSH authentication attempts were recorded.
- Invalid-user events were identified.
- The documented simulation generated 12 failed or invalid authentication events.
- No successful authentication was identified in the reviewed evidence.

### Detection Logic

A threshold of five or more failed or invalid authentication attempts from the same source IP was used as a basis for manual detection analysis.

This was an analytical threshold, not an automated alert.

## 5. T1087.001 — Account Discovery: Local Account

**Tactic:** Discovery

**Technique:** [T1087.001 — Account Discovery: Local Account](https://attack.mitre.org/techniques/T1087/001/)

### Simulation

The lab monitored access to local Linux account-information files.

Monitored files included:

- `/etc/passwd`
- `/etc/group`

### Audit Configuration

```bash
-w /etc/passwd -p r -k account_discovery
-w /etc/group -p r -k account_discovery
```

### Investigation

```bash
sudo ausearch -k account_discovery -i
```

### Observations

Audit events were recorded for access to monitored account-information files.

These events provided information about file access and associated processes.

Because legitimate system activity can also access these files, individual events require contextual investigation before being classified as suspicious.

## 6. T1059 — Command and Scripting Interpreter

**Tactic:** Execution

**Technique:** [T1059 — Command and Scripting Interpreter](https://attack.mitre.org/techniques/T1059/)

### Monitoring Objective

Evaluate command-execution telemetry generated by Linux auditd.

### Audit Configuration

```bash
-a always,exit -F arch=b64 -S execve -F key=command_execution
```

### Benign Commands Tested

```bash
whoami
uname -a
cat /etc/os-release
```

### Investigation

```bash
sudo ausearch -k command_execution -i
```

### Findings

The exercise demonstrated how auditd can record command execution.

These commands were executed as authorized lab tests and were not classified as malicious.

T1059 is included to illustrate the relevance of command-execution telemetry to ATT&CK-based investigations, not as evidence of a confirmed malicious execution technique.

## 7. Splunk Cloud Investigation

Splunk Cloud was used to investigate manually uploaded SSH-related log data.

### SPL Query

```spl
index=main "libssh" | table _time, _raw
```

### Findings

The search returned two SSH-related events containing source IP address `192.168.56.101`.

This exercise demonstrated SIEM event searching and investigation using SPL.

**Mapping limitation:** The observed SSH protocol identification strings do not independently establish brute-force activity. Therefore, the Splunk search results are treated as supporting SSH connection telemetry rather than direct proof of T1110.

## 9. Key Takeaways

- MITRE ATT&CK provides a standardized framework for categorizing adversary behavior.
- Authentication logs can support investigation of brute-force attempts.
- Audit logs provide visibility into account-information access and command execution.
- Security telemetry should be evaluated in context before attributing malicious behavior.
- Splunk Cloud can support investigation through indexed event searches.
- ATT&CK mappings should reflect observed activity rather than assumptions.
